# מודול 12: Agentic Coding Loop — אוטומציה של הלולאה

!!! info "משך"
    30 דקות הרצאה + 60 דקות hands-on + 15 דקות דיון

## מטרות למידה

בסוף המודול הזה, תוכלו:

- להבין את המעבר מ"כתיבת prompts" ל**תכנון לולאות** שכותבות prompts במקומכם
- לבנות לולאת אוטומציה מינימלית שמריצה agent שוב ושוב עד שמשימה מסתיימת
- להבחין בין "האג'נט אומר שהוא סיים" לבין **אימות אובייקטיבי** של סיום
- להכיר את מרכיבי הלולאה האמינה: תזמון, state מתמשך, verification נפרד, וחיבורים מבוקרים
- לזהות את הסיכונים (עלות שמשתוללת, loop אינסופי, איבוד פיקוח) ולהגן מפניהם

!!! tip "למה סשן נפרד?"
    במודול 6 בנינו agent שמגיב לבקשה בודדת — משתמש מקליד, ה-agent פועל, מסיים, וחוזר. אבל מה קורה כשאין משתמש שמקליד את ה-prompt הבא? כאן נלמד לבנות את השכבה שמעל ה-agent: התוכנית הקטנה שמפעילה אותו שוב ושוב במקומכם.

## הרעיון: אתם כבר לא כותבים prompts, אתם מתכננים לולאות

עד עכשיו בסדנה תמיד היה בן אדם שמקליד prompt, קורא את התשובה, ומחליט מה השלב הבא. זה עבד טוב — אבל זה גם צוואר בקבוק: הלולאה "prompt → תשובה → prompt הבא" רצה במהירות של אצבעות על מקלדת.

ברגע שיש לכם agent אמין (זה מה שבנינו במודול 6), אין שום סיבה שבן אדם יהיה החוליה שסוגרת את הלולאה. אפשר לכתוב תוכנית קטנה שעושה בדיוק את זה:

1. שולחת prompt ל-agent
2. קוראת מה הוא הפיק
3. **מחליטה** אם המשימה הושלמה
4. אם לא — שולחת prompt נוסף (אולי מותאם לפי מה שקרה) וחוזרת לשלב 1

זה ה-**agentic coding loop**. במקום "מפעיל agent", אתם הופכים ל"מתכנן/ת לולאות" — התפקיד עובר מלהקליד הוראות בזמן אמת, לעיצוב המערכת שמחליטה מתי להקליד את ההוראה הבאה.

!!! tip "אתם כבר ראיתם את זה"
    ה-skill `/loop` שזמין בסביבת הסדנה עושה בדיוק את זה: מריץ prompt (או slash command) על טיימר קבוע, או עד שתנאי מסוים מתקיים. זה לא קסם — זה תוכנית קטנה שעוטפת agent, בדיוק כמו מה שנבנה בהמשך המודול.

## הגרסה המינימלית: לולאת Bash

הגרסה הכי פשוטה שעדיין שימושית היא כמה שורות bash. אין state מורכב, אין verification חכם — רק לולאה שקוראת ל-agent במצב non-interactive עד שהוא מדווח שסיים, או עד שמגבלת האיטרציות מתמלאת:

```bash
#!/usr/bin/env bash
# loop.sh — מריץ agent שוב ושוב עד שהוא מסמן DONE, או עד למגבלת האיטרציות

MAX_ITERATIONS=10
DONE_MARKER="DONE"
TASK="תקן את הבדיקות הכושלות בתיקיית tests/. כשכל הבדיקות עוברות, כתוב בשורה האחרונה בדיוק: $DONE_MARKER"

for i in $(seq 1 "$MAX_ITERATIONS"); do
  echo "=== איטרציה $i/$MAX_ITERATIONS ==="

  OUTPUT=$(claude -p "$TASK" --output-format text)
  echo "$OUTPUT"

  if echo "$OUTPUT" | tail -1 | grep -q "$DONE_MARKER"; then
    echo "האג'נט דיווח שסיים אחרי $i איטרציות"
    exit 0
  fi
done

echo "הגענו למגבלת האיטרציות בלי DONE — נדרשת בדיקה אנושית"
exit 1
```

זהו. אין כאן שום דבר שלא ראיתם — זה `for` loop שקורא ל-CLI. אבל שימו לב למה שהוא **לא** עושה: הוא סומך על כך שהאג'נט עצמו ידווח "DONE" באמת בכנות. וזו בדיוק הבעיה הראשונה שצריך לפתור.

## הבעיה: אג'נט לא צריך לבדוק את עצמו

בקשה מהאג'נט "תגיד לי אם סיימת" זה כמו לבקש מתלמיד לבדוק את המבחן של עצמו — לפעמים זה יעבוד, אבל אין שום דבר שמחייב את זה. אג'נט יכול:

- לחשוב שהוא סיים כשבעצם נשארה בדיקה כושלת אחת
- "לתקן" בדיקה על ידי שינוי ה-assertion שלה, לא על ידי תיקון הבאג
- להיתקע באותה טעות שוב ושוב בלי לזהות שהוא לא מתקדם

הפתרון: **אימות אובייקטיבי** במקום דיווח עצמי. זה בדיוק אותו עיקרון שראינו במודול 5 (Steering) — לא לשאול את המודל "האם זה עובד?", אלא להריץ את הבדיקות בעצמכם ולתת לתוצאה האמיתית להיות ה-signal:

```bash
#!/usr/bin/env bash
# loop-verified.sh — סיום נקבע על ידי exit code של הבדיקות, לא על ידי דיווח עצמי

MAX_ITERATIONS=10

for i in $(seq 1 "$MAX_ITERATIONS"); do
  echo "=== איטרציה $i/$MAX_ITERATIONS ==="

  claude -p "תקן את הבדיקות הכושלות בתיקיית tests/. הרץ npm test כדי לוודא." \
    --output-format text

  # אימות אובייקטיבי — לא שואלים את המודל, בודקים בעצמנו
  if npm test --silent; then
    echo "כל הבדיקות עוברות אחרי $i איטרציות"
    exit 0
  fi
done

echo "הגענו למגבלת האיטרציות והבדיקות עדיין נכשלות — נדרשת בדיקה אנושית"
exit 1
```

השינוי קטן בקוד אבל גדול בעיקרון: הלולאה כבר לא מאמינה למודל על המילה שלו. היא מריצה משהו דטרמיניסטי (`npm test`) ומחליטה לפי זה.

## חמשת המרכיבים של לולאה אמינה

לולאת ה-bash למעלה עובדת, אבל היא שברירית: אין לה זיכרון בין הרצות, אין לה הגנה מפני עלויות שמשתוללות, ואין לה דרך לעצור ולבקש עזרה כשמשהו לא ברור. לולאה שאמורה לרוץ ללא השגחה צמודה צריכה חמישה מרכיבים:

1. **תזמון (Scheduling)** — משהו שמפעיל את הלולאה על בסיס זמן או אירוע (cron, `/loop`, trigger), במקום שמישהו ירים אותה ידנית בכל פעם.
2. **סביבת הרצה מבודדת** — worktree או branch נפרד לכל ריצה, כדי שלולאות מקבילות (או ריצות חוזרות) לא ידרסו זו את זו.
3. **Memory מתמשך (state file)** — קובץ (JSON או Markdown) שעונה תמיד על שלוש שאלות: על מה עובדים כרגע, מה נכשל בעבר, ומה מחכה לאישור אנושי. בלי זה, כל איטרציה "שוכחת" את מה שקרה באיטרציה הקודמת.
4. **Verification נפרד (maker/checker)** — הצעד שכתב את הקוד לא צריך להיות הצעד ששופט אותו. checker נפרד — בדיקות, לינטר, או אפילו קריאת מודל שנייה עם פרומפט ביקורתי — נותן ציון אמין יותר מ"האג'נט אמר שהוא בסדר".
5. **חיבורים חיצוניים מבוקרים** — אם הלולאה צריכה לפתוח PR, לעדכן טיקט, או לשלוח הודעה, זה קורה דרך אינטגרציה מוגדרת (כמו שרתי MCP, שנלמד עליהם במודול הבא) — לא shell פתוח שיכול להריץ כל דבר.

הנה איך זה נראה עם state file פשוט:

```json
{
  "task": "הוסף טיפול בשגיאות לכל ה-API endpoints ב-src/routes/",
  "iteration": 3,
  "maxIterations": 10,
  "status": "in_progress",
  "history": [
    { "iteration": 1, "result": "טופלו 2/5 endpoints", "testsPass": false },
    { "iteration": 2, "result": "טופלו 4/5 endpoints", "testsPass": false },
    { "iteration": 3, "result": "טופלו 5/5 endpoints", "testsPass": true }
  ]
}
```

ולולאה שקוראת אותו, עם maker/checker מופרד:

```typescript
import { execSync } from "child_process";
import * as fs from "fs";

interface LoopState {
  task: string;
  iteration: number;
  maxIterations: number;
  status: "in_progress" | "done" | "needs_human" | "failed";
  history: { iteration: number; result: string; testsPass: boolean }[];
}

function loadState(path: string): LoopState {
  return JSON.parse(fs.readFileSync(path, "utf-8"));
}

function saveState(path: string, state: LoopState): void {
  fs.writeFileSync(path, JSON.stringify(state, null, 2));
}

function runTests(): boolean {
  try {
    execSync("npm test", { stdio: "pipe" });
    return true;
  } catch {
    return false;
  }
}

async function runLoopIteration(state: LoopState): Promise<LoopState> {
  // maker — האג'נט מבצע את המשימה
  execSync(`claude -p "${state.task}. זו איטרציה ${state.iteration}."`, {
    stdio: "inherit",
  });

  // checker — בדיקה אובייקטיבית, לא דיווח עצמי
  const testsPass = runTests();

  state.history.push({
    iteration: state.iteration,
    result: testsPass ? "בדיקות עוברות" : "בדיקות נכשלות",
    testsPass,
  });

  // עצירה אם אין התקדמות בין שתי איטרציות אחרונות
  const last = state.history.slice(-2);
  const stuck =
    last.length === 2 && last[0].testsPass === last[1].testsPass && !testsPass;

  if (testsPass) {
    state.status = "done";
  } else if (state.iteration >= state.maxIterations) {
    state.status = "needs_human";
  } else if (stuck && state.iteration > 3) {
    state.status = "needs_human"; // אין התקדמות — לא ממשיכים לבזבז iterations
  } else {
    state.iteration++;
  }

  return state;
}
```

שימו לב לתנאי העצירה: יש שלושה, לא אחד — `testsPass` (הצלחה אמיתית), `iteration >= maxIterations` (הגנת עלות/זמן), ו-`stuck` (זיהוי שהלולאה לא מתקדמת, כדי לא להריץ עוד 7 איטרציות סתם). כל אחד מהם מוביל ל-`needs_human` — לא לקריסה שקטה.

## הגנות חובה (Guardrails)

לולאה שרצה ללא בן אדם שמאשר כל צעד היא גם לולאה שיכולה לצבור נזק גדול לפני שמישהו שם לב. חובה:

- **תקרת איטרציות** — ראינו למעלה. בלי זה, באג בלוגיקת הסיום = לולאה אינסופית שמבזבזת tokens.
- **תקציב עלות/tokens** — הגדירו סף לכמות tokens או עלות בדולרים לריצה שלמה, לא רק לאיטרציה בודדת.
- **Timeout לכל איטרציה** — אג'נט שנתקע (למשל, מחכה לקלט שלא יגיע) לא צריך לתקוע את כל הלולאה.
- **Sandbox להרצת פקודות** — בדיוק כמו שראינו במודול 6 עם `run_command`: לולאה אוטונומית לא צריכה גישה בלתי מוגבלת לשל shell.
- **עצירה לפני פעולות בלתי הפיכות** — `git push`, מחיקת קבצים, deploy — הלולאה צריכה לעצור ולסמן `needs_human`, לא לבצע אוטומטית.

!!! danger "הסכנה: איבוד פיקוח (Cognitive Surrender)"
    כשלולאה עובדת "לבד" זמן ארוך, קל מאוד להפסיק לעקוב אחרי מה שהיא עושה בפועל. זה מסוכן — היא יכולה לצבור עשרות איטרציות של קוד גרוע לפני שמישהו שם לב שמשהו השתבש. תמיד: תעדו כל איטרציה (ה-`history` array למעלה), הגדירו checkpoint לבדיקה אנושית (כל N איטרציות, או כשה-status עובר ל-`needs_human`), ולעולם אל תתנו ללולאה גישה ל-production בלי אישור אנושי מפורש.

## מושגים מפתח

### Loop Engineering

המעבר המחשבתי מ"כתיבת prompt בודד" ל"תכנון המערכת שמחליטה איזה prompt לשלוח הבא". אתם לא מפעילים agent — אתם מעצבים את הלולאה שמפעילה אותו.

### Maker/Checker

הפרדה בין הצעד שמבצע את העבודה (maker) לצעד שמאמת אותה (checker) — מודל, פרומפט, או כלי שונים לכל אחד, כדי שאף אחד לא בודק את עצמו.

### Completion Signal

הדרך שבה הלולאה יודעת שהיא סיימה. דיווח עצמי מהמודל הוא הכי קל למימוש והכי לא אמין; אימות אובייקטיבי (בדיקות, לינטר, exit code) הוא הכי אמין.

### State File

קובץ מתמשך שהופך כל איטרציה ל"מודעת" למה שקרה קודם — בלעדיו, כל הרצה של הלולאה מתחילה מאפס.

## נקודות מפתח

- Agentic coding loop הוא תוכנית קטנה: `prompt → קרא תוצאה → החלט אם סיימנו → prompt נוסף אם לא`
- הגרסה המינימלית היא שורת bash אחת עם לולאה; גרסה מעשית משתמשת ב-state file ו-verification נפרד
- **לעולם** אל תסתמכו על דיווח עצמי של המודל כאות סיום — השתמשו באימות אובייקטיבי (בדיקות, exit codes) בכל מקום שאפשר
- לולאה אמינה צריכה חמישה מרכיבים: תזמון, סביבה מבודדת, memory מתמשך, verification נפרד, וחיבורים חיצוניים מבוקרים
- הגנות חובה: תקרת איטרציות, תקציב עלות, timeout, sandbox, ועצירה לפני פעולות בלתי הפיכות
- לולאה אוטונומית לא פוטרת אתכם מפיקוח — היא מחייבת תיעוד וצ'קפוינטים אנושיים ברורים, אחרת אתם מסתכנים ב"איבוד פיקוח"

### מה הלאה

זה המודול המתקדם האחרון בסדנה. במודול הבא — פרויקט הגמר — תשלבו הכל: prompt engineering, agent שבניתם מאפס, MCP, skills, sub-agents, ודפוסי production, ואפשר גם להריץ אותו כ-agentic coding loop אם תרצו.
